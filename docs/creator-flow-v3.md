# Creator flow v3 — paid plan review

New custom orders use `creatorVersion: 3`. Existing v1/v2 paid order snapshots keep their original fulfillment contract. Before payment, the creator collects the idea, group, physical venue, fictional story setup and supported play styles. It shows a fixed five-checkpoint format example, independent play sample, real PDF format example, price and rights. The free `/api/v1/proposals` route is closed by default; `LEGACY_PROPOSALS_ENABLED=true` exists only for isolated legacy tests. Do not enable it on the public site.

Run migration `0008_custom_plan_review.sql` before allowing v3 checkout. New custom offers fail closed if the plan table is absent. Stripe fulfillment creates the custom activity and entitlement but queues a **plan** job, not a PDF job. Duplicate webhooks and scheduled retries requeue the appropriate pending job. The custom activity remains queued while the order stays paid.

The first plan is included. A customer can request up to two successful whole-plan reworks and three successful targeted edits (title, summary, opening, roles, goal, preparation or one checkpoint). Feedback requires 10–500 characters. Requests use an idempotency key and are serialized per order. Plan schema/structure validation, meaningful-change checks and an independent model audit run before a version is stored and a change counter increments. Failed requests retry up to three times without using a customer change; after repeated failure the order shows `needs_help` for support. Earlier versions remain selectable without consuming a change.

`POST /api/v1/orders/:id/plan` accepts `rework`, `edit`, `select` or `confirm` for the authenticated purchaser. Only `confirm` snapshots the chosen plan into `custom_activities.story_spec_json` and queues full generation. Both queue and scheduler refuse v3 PDF generation without a confirmed plan. Post-delivery single-checkpoint revisions use the approved activity spec. Existing two-successful-revisions/30-day and 12-month redownload rights remain separate.

Support and refund requests use the existing order issue form. Do not promise an automatic refund. Provider/token costs are recorded in `generation_usage` per order attempt. The test checkout and local scripted demo are not proof of live payment or live AI quality; validate a real paid plan and PDF in staging before deployment.
